# Roadmap: computer-vision + RL overhaul of PokemonRedRL

Status: Reviewed

> **How to read this plan.** This is an *epic-level* roadmap, not a single implementation task. Its "Steps" are an ordered list of **separate future tasks**, each of which will get its own `docs/tasks/<slug>.md` (via `/plan-task`) and its own `/review-plan` → `/implement-task` → `/review-changes` → `/commit-changes` cycle when it's picked up. This file's job is to sequence them correctly, record the cross-cutting decisions and risks that span multiple tasks, and give the user one place to see the whole arc. Treat each `- [ ]` below as "spin up its own plan when we get here", not as a literal file edit.

## Goal

Turn PokemonRedRL from a memory-state-only DQN agent into one with (a) computer-vision-augmented perception feeding both the policy and reward shaping, (b) a deliberately chosen/validated RL algorithm rather than an un-benchmarked default, (c) durable model/knowledge persistence, and (d) a modernized, correctly-configured .NET/package baseline — while reusing the existing 5-project architecture, Redis-backed multi-agent training loop, and emulator bridge wherever it still makes sense, per the user's explicit direction to build on what's here rather than discard it outright.

## Affected files/projects

Ultimately: all 5 C# projects, both `mgba_socket.lua` copies (and their long-standing divergence — see Task 2), `Program.cs` DI wiring, `docs/PROJECT_OVERVIEW.md` §7 (to be updated from "planned" to "current" as each piece lands), `docs/CODEBASE_MAP.md`, and likely a new `PokemonRedRL.Vision` project. Exact file lists belong in each sub-task's own plan, not here.

## Steps (ordered list of future sub-tasks)

- [x] **Task 1 — Spike: validate the frame-capture mechanism. RESOLVED.** Real, measured results (see [docs/tasks/frame-capture-spike.md](frame-capture-spike.md)): `emu:screenshot()` + file read achieves only **~1.0 Hz** (fails even the 1x bar of ~4 Hz); direct OS-level window capture (`PrintWindow`) achieves **~141–145 Hz** with no degradation at 3 concurrent windows, clearing the 10x-fast-forward bar (~40 Hz) with large headroom. **Decision: vision will use OS-level window capture, correlated to each agent via its process handle at launch time (not window title matching).** Candidate (c) (mGBA 0.11 framebuffer API) was skipped — confirmed still unreleased (current stable is 0.10.5, matching what's vendored; no preview release exists as of this research). No emulator upgrade is needed.
- [x] **Task 2 — Pre-overhaul cleanup of known debt. RESOLVED.** **Narrowed per user decision** ([docs/tasks/pre-overhaul-cleanup.md](pre-overhaul-cleanup.md)): fixed the `RewardCalculatorService` badge/level staleness bug (now updates `_previousBadges`/`_previousLevels`), removed the duplicate `IExperienceRepository` DI registration (kept `Singleton`), deleted the stale `src/scripts/mgba_socket.lua`, fixed the hardcoded absolute Lua `package.path`/`package.cpath` (now resolved relative to the script's own location, verified with a real mGBA smoke test), and removed the unused `Parquet.Net` package reference from `PokemonRedRL.Utils`/`PokemonRedRL.Core`/`PokemonRedRL.Agent`. `ExperienceReplay`/`MemoryCache`/`SumTree` were kept as-is (only documented as unused, not deleted, per user decision). The launch-automation and fast-forward items originally bundled here are split out — see Task 2b.
- [x] **Task 2b — Desktop control panel for emulator orchestration and training monitoring. RESOLVED (MVP implemented, one known limitation).** `PokemonRedRL.ControlPanel` (WPF, `net8.0-windows`) shipped per [docs/tasks/automated-mgba-launch-and-fast-forward.md](automated-mgba-launch-and-fast-forward.md): run manifest (`RunManifest`/`AgentSlot`) with isolated per-slot runtime directories, one `PokemonRedRL.Agent` process per emulator slot (`Program.cs` `--port`/`--agent-index` mode), exact per-slot telemetry via a `STATUS ...` stdout line (no heuristic log matching), an adaptive 1–9 paginated emulator wall with `PrintWindow` previews throttled to 10 FPS/tile, and explicit user-driven window attachment (deliberately not automatic — no reliable port↔window OS signal exists). **Known limitation, confirmed not assumed:** automated mGBA launch is blocked — the vendored 0.10.5 binary has no `--script` flag (pre-dates that upstream feature), and the locally Docker-built upstream binary only produced an SDL frontend (no `--script` support there either; only the unbuilt Qt frontend has it in source). Shipped mode is **manual attach only**: the user starts each mGBA instance and loads the bridge script by hand; the control panel discovers/monitors/tears down from there. `launch_agents.bat`'s `--port`/`--script` flags remain nonexistent on stable mGBA 0.10.5, confirmed via live `--help` output. Real 1/3/10-instance scale verification with live mGBA windows was **not** performed in the implementation pass (requires manual user setup) and is recorded as an outstanding follow-up in the plan's Step 12.
- [x] **Task 3 — .NET & package modernization. RESOLVED.** ([docs/tasks/net-package-modernization.md](net-package-modernization.md)): TFM bumped `net8.0` → `net10.0` across all 6 projects; TorchSharp + TorchSharp-cuda-windows 0.105.0 → 0.107.0 (LibTorch 2.10.0, CUDA 12.8 — verified `cuda.is_available() == true` on RTX 4070 SUPER); MessagePack 3.1.3 → 3.1.8 (resolved all NU1902/NU1903 advisories); StackExchange.Redis 2.8.31 → 3.1.31; Microsoft.Extensions.* 9.0.4 → 10.0.11; Parquet.Net fully removed (package + `[ParquetIgnore]` attributes); System.Net.Sockets 4.3.0 shim removed; OpenCvSharp4 + OpenCvSharp4.runtime.win 4.13.0.20260627 added to `PokemonRedRL.Utils` as a dependency placeholder for Task 6. Docs updated.
- [ ] **Task 4 — Design the combined (vision + memory-state) representation.** Write a short design doc/ADR (or a `docs/PROJECT_OVERVIEW.md` update) settling: hybrid dual-branch network (CNN branch for frames + existing MLP branch for the 14-float memory vector, fused before the Q-head) vs. pixels-only — this roadmap's working recommendation is **hybrid**, per the reasoning in `docs/PROJECT_OVERVIEW.md` §7, but this task is where that gets confirmed or overridden; frame preprocessing spec (grayscale vs. color, resize target, frame-stack depth for motion, normalization); how much this changes the existing `[HP, MapID, X, Y, Direction, Badges, InTrainerBattle, Money, PartyLevels[0-5]]` vector (keep as-is, or trim now-redundant positional features if vision covers them); and **a feature flag / config switch to disable the vision branch entirely**, so the pre-vision memory-only baseline stays runnable side-by-side for comparison once vision lands — without this, there's no way to tell whether vision is actually helping versus just adding compute cost and instability.
- [ ] **Task 5 — RL algorithm review.** Deliberate research/decision task (not an assumption), done *before* building new trainer code around it: reason through staying with Double-DQN + prioritized replay vs. adding Rainbow-style improvements (dueling heads, n-step returns, noisy nets) vs. switching to an on-policy method (PPO) — document the tradeoffs given this project's specific constraints (real-time emulator rollouts, multi-agent Redis-shared learning, no existing benchmark/eval harness to compare against, and now GPU/VRAM budget across `NUMBER_OF_AGENTS` parallel agents once a CNN branch is added — see the new GPU-capacity risk below). Roll Task 2's reward-bug fix into whatever eval harness this task produces, so the algorithm choice is judged on a corrected reward signal. **This must land before Task 8**, since Task 8 builds the actual trainer code around whichever algorithm is chosen here — building the dual-modality DQN trainer first and then swapping algorithms afterward would waste that work.
- [ ] **Task 6 — `PokemonRedRL.Vision` project + frame acquisition/preprocessing pipeline.** New project following the existing `Interfaces/`+`Services/` convention (`IFrameProvider`/`IVisionPreprocessorService`), implementing **OS-level window capture (`PrintWindow`)** per the Task 1 decision — consume the Task 2b control panel's run manifest to correlate each captured window to its owning agent via process/window handle, not window-title matching (titles aren't distinguishable across instances); producing a ready-to-consume `Tensor` (or raw buffer) per requested frame; include basic performance instrumentation (capture latency, dropped-frame rate) since this runs inside the hot per-step loop. Include the new `IFrameProvider`/`IVisionPreprocessorService` DI registrations in `Program.cs`, following the existing `Scoped` (per-agent/connection state) vs. `Singleton` (shared infra) convention explicitly — don't leave this implicit for the sub-task's own plan to rediscover.
- [ ] **Task 7 — (Re-scoped after Task 1) No frame-delivery protocol change is needed** — since vision uses OS-level window capture, not a new Lua command, this task is no longer "extend the bridge protocol" as originally planned. Repurposed to: verify no *other* protocol changes are needed for vision to coexist with the existing memory-state TCP bridge (they're independent capture paths), and land the minimal contract test originally planned here (serialize/deserialize a sample `GameStateResponse` payload against `GameStateSerializer`) as a low-cost regression guard, since it's still valuable independent of the frame-capture mechanism.
- [ ] **Task 8 — Dual-modality network + trainer support.** New/extended network (e.g. `PokeVisionDQN`, or whatever architecture Task 5 settled on) implementing Task 4's representation design; extend `ModelExperience`/`GameState`/`StatePreprocessorService` to carry both modalities; update the trainer for dual-tensor batches. Explicitly re-evaluate Redis storage strategy here — raw frames are far larger than the current 14-float vector, so decide between storing compressed/downsized frames vs. only CNN embeddings in `RedisExperienceRepository`, with a concrete estimate of per-experience payload size and expected Redis memory footprint at the existing `MaxStreamLength`/`BatchSize` settings (`RedisConfig`) before committing. Also register any new/changed services in `Program.cs`'s DI container explicitly, matching existing lifetimes.
- [ ] **Task 9 — Vision-aware reward shaping.** Depends on Task 6 (frames available) and Task 2 (reward-bug fix already in place so shaping isn't built on top of a known-broken signal) — **does not need to wait for Task 5/8's algorithm choice**, since reward computation is algorithm-agnostic; sequence it right after Task 6 if convenient rather than pushing it to the end by default. Extend `RewardCalculatorService` with visual-novelty/progress signals (e.g. perceptual-hash or embedding-distance novelty bonus as a complement to the existing map/x/y-based novelty bonus, visual dialogue/menu-state detection to adjust exploration).
- [ ] **Task 10 — Model persistence & "knowledge storage" redesign.** Currently the only persistence is periodic full `state_dict` push/pull to a single Redis key plus separate LR-scheduler state — nothing loads weights back from local disk at startup, so a Redis flush loses all training progress. Design versioned on-disk checkpoints under `src/data/models/` (intentionally-committed backups per repo convention), checkpoint metadata (step count, smoothed reward, epsilon), and a resume-on-restart flow that doesn't depend solely on Redis being warm.
- [ ] **Task 11 — Testing infrastructure.** Add the still-missing `xUnit` test project; prioritize the pure-logic pieces that are now easiest to regression-test after this overhaul: `RewardCalculatorService` (including a regression test for the Task 2 bug fix), `StatePreprocessorService`, the new vision preprocessing math, `SumTree`/replay sampling. (The Lua-protocol contract test is pulled forward into Task 7 itself, not deferred here.)
- [ ] **Task 12 — Documentation catch-up.** After each of the above lands, fold its "planned" language in `docs/PROJECT_OVERVIEW.md` §7 into normal present-tense documentation (or move it back into §1–6 as appropriate), and run `/cartograph` to refresh `docs/CODEBASE_MAP.md`. Treat this as a recurring checklist item inside *each* task's own `/implement-task` pass (per the existing repo workflow) rather than a single task done once at the end.

## Risks & irreversible actions

- **Task 1 is RESOLVED** — OS-level window capture (`PrintWindow`) is the validated mechanism, ~141–145 Hz, no degradation at 3 concurrent windows. Architecture work (Task 4 onward) may now proceed without this blocker.
- **Task 5 (RL algorithm review) must precede Task 8 (trainer build).** Building dual-modality DQN-specific trainer code before the algorithm choice is confirmed risks throwing that work away if the review concludes something other than DQN is a better fit.
- **Protocol changes (Task 7) are two-sided and hard to verify automatically** — no CI, no Lua test runner; every change needs a real mGBA manual smoke test before being trusted, per existing repo convention.
- **Redis payload size (Task 8)** is a real capacity risk once frames enter the experience stream — could silently blow up Redis memory usage or `MaxStreamLength` behavior if not sized deliberately first.
- **TorchSharp tensor lifecycle risk gets materially worse with vision.** The current codebase already requires care around `Tensor` disposal (`DQNTrainer` uses `NewDisposeScope`/manual `Dispose()` calls); frame tensors are orders of magnitude larger than the existing 14-float state vector, so a leak that was a slow memory creep before could become a fast OOM crash once every experience carries an image. Task 6/8 must treat tensor disposal as a first-class concern, not an afterthought, and should include a short soak-test (run N steps, watch process memory) as part of their own verification plans.
- **GPU/VRAM capacity is an unresourced risk.** Adding a CNN branch increases per-step compute and memory cost substantially; running `NUMBER_OF_AGENTS` (currently 10) parallel agents each doing CNN inference/training on shared GPU hardware may not fit in available VRAM. Task 5 (algorithm review) and Task 8 (trainer) should both explicitly budget for this (e.g. measure actual VRAM usage with 1 agent before assuming it scales linearly to 10, and have a fallback plan — fewer concurrent vision-enabled agents, smaller CNN, or batching frame inference — ready if it doesn't fit).
- **.NET/package upgrades (Task 3)** touch every project's `.csproj` — do them behind their own build-and-run verification, one package/TFM change at a time, not as a single giant diff, to keep bisectable if something regresses (especially TorchSharp/CUDA compatibility, which is easy to silently break).
- **An emulator version upgrade, if Task 1 concludes it's needed, is an unbudgeted risk of its own** (new binary, Lua library compatibility, launch script/config updates) — do not let it get silently absorbed into Task 1 or Task 7's scope; treat it as its own discovered task with its own plan if it turns out to be necessary.
- **Nothing here should be done as a single mega-PR.** Each numbered task above must go through its own `/plan-task` → `/review-plan` → `/implement-task` → `/review-changes` → `/commit-changes` cycle so `/review-changes` can actually verify a bounded diff.
- No git-history rewrites, force-pushes, or ROM/save-state deletions are anticipated anywhere in this roadmap.

## Verification plan

- Each sub-task defines its own verification plan when planned individually (this is intentional — a vision-pipeline task and a package-bump task need very different verification).
- Roadmap-level success criteria to keep in view across all sub-tasks: (1) full solution still builds and the multi-agent training loop still runs end-to-end against a real mGBA instance after every task, not just at the very end; (2) the reward signal is demonstrably not double/over-firing after Task 2's bug fix (spot-check via logged rewards over a short run); (3) frame-capture throughput (Task 1/6) doesn't become the bottleneck relative to existing memory-state polling; (4) the Task 4 feature flag lets the pre-vision baseline still run and be compared against, at every later stage, not just before vision work starts.

## Open questions/assumptions

- **.NET target version** (Task 3): this plan assumes .NET 10 (current LTS) is the right target; needs confirming against actual current .NET support status and TorchSharp/OpenCvSharp compatibility at implementation time, not assumed permanently correct from this document's writing date.
- **CV library choice**: OpenCvSharp4 is this plan's working assumption for any real image-processing needs (resize/grayscale/normalize can arguably be done with plain TorchSharp tensor ops without OpenCV at all, if preprocessing stays simple) — Task 4/6 should confirm whether OpenCV is actually needed or if TorchSharp alone suffices, rather than adding a heavy native dependency by default.
- **Hybrid vs. pixels-only architecture** (Task 4): this roadmap recommends hybrid by default; flagged explicitly for the user to confirm or override during `/review-plan`, since it's the single most consequential design decision in this whole roadmap.
- **Scope of "start from scratch"**: interpreted as "aggressively redesign RL/vision/reward logic, but keep the existing 5-project layout, Redis-backed multi-agent training loop, and DI conventions unless a specific task finds a concrete reason to replace them" — flagging this interpretation explicitly in case the user meant a more literal rewrite.
- **Frame-capture performance ceiling — RESOLVED.** OS-level window capture measured at ~141–145 Hz single- and 3-instance. No roadmap scope reduction needed on this front. Task 2b now owns stable window-handle/process mapping through the desktop control panel; Task 6 should consume that manifest rather than rediscovering windows.
- **GPU/VRAM budget** (Task 5/8, new): no current measurement exists of per-agent GPU memory/compute cost, with or without a CNN branch — needs an early empirical measurement (even a rough one) rather than being assumed to scale linearly.

⚠️ **Gaps found and fixed in this revision:**
- **Ordering problem:** the RL algorithm review was sequenced *after* building the dual-modality DQN trainer, risking thrown-away trainer work if the review picked a different algorithm. Fixed by moving the algorithm review earlier (now Task 5, before the trainer build).
- **Missing risk:** TorchSharp tensor disposal — already a known sharp edge in this codebase (`DQNTrainer`'s manual `Dispose()`/`NewDisposeScope` calls) — wasn't called out at all for the much-larger frame tensors vision introduces. Added as an explicit risk with a soak-test recommendation.
- **Missing risk:** no consideration of GPU/VRAM capacity for running a CNN branch across `NUMBER_OF_AGENTS` (10) parallel agents. Added as an explicit risk and open question requiring an early empirical measurement.
- **Missing contingency:** if Task 1's spike concludes the emulator itself needs upgrading (mGBA 0.11+) to get a usable frame API, that's a nontrivial task of its own (new binary, Lua library compatibility, launch script updates) that wasn't accounted for anywhere. Now explicitly called out as a discovered task, not silently absorbed into Task 1 or the protocol-change task.
- **Weak justification for a false dependency:** vision-aware reward shaping was gated on the RL algorithm review finishing, even though reward computation is algorithm-agnostic. Loosened so it only depends on the frame pipeline and the reward-bug fix, and can move earlier if convenient.
- **Deferred testing that didn't need to be:** the Lua-protocol contract test was pushed all the way to the final testing task; pulled forward into the protocol-change task itself so drift is caught the moment the protocol changes, not much later.
- **Missing DI-wiring reminders:** per `/review-plan`'s standing checklist, explicitly added "register in `Program.cs` with the correct lifetime" reminders to the vision-pipeline and dual-modality-trainer tasks, rather than leaving it implicit for each sub-task's own plan to rediscover.
